Guide

What each phase buys you

Every phase in the explore → plan → code → verify loop removes a class of failure. This page maps each phase to the failure it prevents — and to the check that would have caught it.

A model, not an LLM. The lab is a scripted simulation: it shows what each phase contributes, not the internals of any real agent.

Start here

What this demo proves

The same task — 10% off orders ≥ $100 — run three ways on a codebase with hidden conventions: money is integer cents, one shared totals.mjs feeds both cart and invoice, and adjustments must appear as invoice lines. Prompt-first produces plausible work that fails three checks nobody ran. Verify-only catches them after the wrong work is done. The full loop passes on the first verified run — because the implement step is built from facts, not guesses.

Run it in the lab

The loop

Four phases, four failure classes

Phase 01

Explore

Reading files yields facts that are invisible from the task text: shared totals, integer-cents math, the line-item convention, the existing test suite.

Skip it
The agent writes the "obvious" change — duplicated logic in cart.mjs, float math, silent totals.
Phase 02

Plan

A written plan turns "vibes" into a reviewable artifact — steps that name the files and conventions they depend on.

Skip it
Nothing to approve; a wrong approach costs a whole implementation instead of a plan revision.
Phase 03

Implement

The code an agent writes is a direct function of what it knows: the variant it picks is chosen by discovered facts.

Watch for
Partial knowledge produces partial failures — skip invoice.mjs and the audit line never appears.
Phase 04

Verify

A runnable check (tests, build, screenshot diff) gives the loop a stop condition and turns "done" into evidence.

Skip it
"Looks done" is the only signal — feature-works passes in every variant while three checks fail latent.

Inspect the evidence

Toggle phases and file reads in the lab — partial explores produce partial failures.

Limits

What this demo does not claim

  • It is a scripted model of the workflow — no LLM runs; it demonstrates what each phase contributes, not any agent's internals.
  • The four checks stand in for a real test suite — real projects need real tests wired as the agent's stop condition.
  • Facts here are all-or-nothing; real exploration yields degrees of understanding.
  • The "agent" never argues back — real sessions need course-correction, not just a pipeline.
